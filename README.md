# Kiho PDF

브라우저에서만 동작하는 PDF 편집기. 서버·업로드가 없어 대용량 파일도 즉시 열리고, 저장은 무손실이다.
한 번 방문하면 오프라인에서도 동작한다(PWA).

## 실행

```bash
npm install
npm run dev        # http://localhost:5173
npm run build      # dist/ 에 정적 파일 생성 (아무 정적 서버·하위 경로에 올려도 된다)
npm run preview    # http://localhost:4173 에서 빌드본 확인(서비스 워커·오프라인 포함)
npm run typecheck  # 타입 검사
npm test           # 단위 테스트 (vitest)
npm run e2e        # E2E (Playwright, 설치된 Edge 사용 — 브라우저 다운로드 없음. Chrome: PW_CHANNEL=chrome)
```

- Node.js 24 LTS 기준(`.nvmrc`). 22.12 이상이면 동작한다. Docker 는 필요 없다.
- Chrome/Edge 권장: File System Access API 로 폴더를 한 번만 고르면 분할 파일을 대화상자 없이 기록한다.
  미지원 브라우저에서는 무압축 ZIP 으로 내려받는다. 이 API 와 서비스 워커는 `https` 또는 `localhost` 에서만 동작한다.
- 배포는 [docs/DEPLOY.md](docs/DEPLOY.md)(GitHub Pages 권장, Firebase Hosting·FTP 절차 포함), 변경 이력은 [CHANGELOG.md](CHANGELOG.md).
- 이어서 작업하는 사람은 [docs/HANDOFF.md](docs/HANDOFF.md)(현재 상태 · 열려 있는 일 · 함정 · 작업 기록)부터 읽는다.

### 설치형 앱(PWA)

주소창의 설치 아이콘으로 앱처럼 설치할 수 있다. 설치하면 PDF 파일의 "연결 프로그램"에 나타나고(`manifest.webmanifest` 의
`file_handlers`), 그렇게 연 파일은 바로 편집 화면에 뜬다. 한 번 접속한 뒤에는 인터넷 없이도 동작한다.

## 화면

| 영역 | 내용 |
|---|---|
| 좌측 위 | 현재 페이지. 기본 배율 75%(100% = 96dpi). 높이는 `750px × 배율`, 분할선을 끌어 조절(더블클릭 = 자동) |
| 좌측 아래 | 전체 페이지 썸네일(가상 스크롤). 클릭 = 이동, Ctrl/Shift+클릭 = 다중 선택, 끌기 = 순서 변경 |
| 우측 | 파일 · 보기 · 분할 · 캡처 · 페이지 · 편집 탭, 실행 취소 / 다시 실행 / 도움말 |

### 파일 (파일 탭)

- **열기**: 버튼, `Ctrl+O`, 또는 PDF 를 창에 끌어다 놓기. 암호가 걸린 파일은 암호를 묻는다.
- **다른 PDF 삽입(병합)**: 현재 쪽 뒤에 다른 PDF 의 모든 쪽을 끼워 넣는다(여러 파일 가능). `Shift` 를 누른 채 파일을 끌어다 놓아도 된다.
- **저장**(`Ctrl+S`): 항상 무손실, 다른 이름으로 저장. 열려 있는 원본과 같은 파일에 덮어쓰면 저장본으로 자동으로 다시 열리며
  보던 쪽·분할 그룹·캡처 목록이 그대로 이어진다.
- **인쇄**(`Ctrl+P`): 브라우저의 PDF 인쇄 기능을 그대로 쓴다(벡터 유지).
- **용량 최적화 저장(선택)**: 아래 "파일 크기 정책" 참고.
- **전자서명이 있는 문서**는 문서 정보에 표시되고, 저장 전에 한 번(문서마다) 확인을 받는다. 이 앱으로 저장한 파일에서는 서명이 무효가 된다.
- 닫기 · 새로 열기 · 창 닫기 때 저장하지 않은 변경 사항이나 아직 이미지로 저장하지 않은 캡처가 있으면 먼저 알린다.

### 보기 (보기 탭)

- 쪽 번호 입력, ◀ ▶ ⏮ ⏭, 배율(− / ＋, 50·75·100·150%, 너비 맞춤, 쪽 맞춤, `Ctrl+휠`), 목차(북마크) 이동.

### 일괄 분할 (분할 탭)

문서를 넘기다가 묶음의 마지막 쪽에서 `Enter` → 파일명 입력 → `Enter`(다음 쪽으로 이동)를 반복한 뒤 **모두 저장**.
썸네일 사이의 ✂ 로 분할 지점을 토글할 수도 있고, N쪽마다 · 북마크 기준 · 범위 목록 붙여넣기(`1-5 계약서`)로 한 번에 만들 수도 있다.
이름 템플릿: `{원본} {번호:02} {시작} {끝} {쪽수}`.

### 캡처 (캡처 탭, 단축키 `C`)

쪽 위의 임의 영역을 이미지로 담는다. 분할과 같은 방식으로 **목록에 모아 두었다가 한꺼번에 파일로 저장**한다.

1. `C` 로 영역 캡처 도구를 켜고 쪽 위를 드래그 → 놓는 즉시 목록에 담긴다. 도구는 켜진 채 남으므로 쪽을 넘기며 계속 담는다.
   "현재 쪽 전체 담기" 로 쪽 전체를 담을 수도 있다.
2. 목록에서 이름을 고치거나(템플릿 `{원본} {쪽} {번호:02}`) 미리보기를 눌러 그 쪽으로 이동한다. ⧉ 는 한 장을 클립보드로 복사.
   영역을 고치려면 `Esc` 로 도구를 끄고 초록 상자를 눌러 옮기거나 크기를 바꾼다(`Delete` 삭제, 실행 취소 가능).
3. 해상도(96–600dpi, 기본 300)와 형식(PNG 무손실 / JPEG)을 고르고 **모두 저장** → 폴더를 한 번만 고르면 끝(미지원 브라우저는 ZIP).

화면을 찍는 것이 아니라 **PDF 에서 그 영역만 고른 해상도로 다시 렌더**하므로 화면 배율과 무관하게 선명하고, 삽입한 텍스트·펜 선도 포함된다.
영역은 쪽 좌표로 보관하므로 캡처한 뒤 쪽을 회전해도 같은 내용을 가리킨다. 목록은 임시 보관이라 문서를 닫으면 사라지지만,
이미지로 저장하지 않은 캡처가 있으면 닫기 전에 알려 주고, PDF 를 원본에 덮어써서 다시 열릴 때는 목록이 유지된다.

### 페이지 (페이지 탭)

대상은 선택한 썸네일(없으면 현재 쪽). 왼쪽 / 오른쪽 / 180° 회전, 전체 회전, **추출하여 저장**(고른 쪽만 새 PDF 로),
삭제(실행 취소 가능), 맨 앞으로 / 맨 뒤로. 순서는 썸네일을 끌어서도 바꾼다. 삽입한 텍스트·펜 선과 캡처 영역은 쪽과 함께 돈다.

### 편집 (편집 탭)

| 도구 | 키 | 동작 |
|---|---|---|
| 선택 | `V` | 삽입 항목 선택·이동, `Delete` 삭제. 빈 곳에서는 본문 글자 선택·복사 |
| 텍스트 | `T` | 드래그(또는 클릭)한 자리에서 바로 입력. 상자 밖을 누르면 확정 |
| 펜 | `P` | 자유 곡선(서명·체크 표시). 색·굵기 선택 |

편집 중에는 PDF 를 건드리지 않고 오버레이로만 보관한다. 저장할 때 기존 콘텐츠를 `q…Q` 로 감싼 뒤
**새 콘텐츠 스트림으로 덧붙이므로** 기존 그래픽 상태와 충돌하지 않는다. 회전(/Rotate)·CropBox 가 있는 쪽에서도
화면에서 본 위치·방향 그대로 들어간다. 한글 폰트(Pretendard)는 사용한 글자만 서브셋으로 포함되고,
줄바꿈은 화면과 저장본이 같은 계산을 쓴다.

**다시 고치기**: 저장할 때 삽입 항목의 기록을 쪽의 `/PieceInfo`(응용 프로그램 전용 자료를 두는 PDF 표준 자리)에 함께 적고,
문서 정보(Info)에 `KihoEdits` 표시를 남긴다. 이 앱에서 그 파일을 다시 열면 덧붙였던 콘텐츠 스트림을 걷어 내고 같은 항목을
편집 가능한 상태로 되살린다(`src/engine/pieceInfo.ts`). 표시가 없는 파일은 문서 정보만 확인하므로 여는 속도에 영향이 없다(측정: 3–5ms).
다른 프로그램이 파일 구조를 바꿔 놓아 덧붙인 스트림을 찾을 수 없으면 그 쪽은 건드리지 않고 본문에 고정된 채로 연다.

### 도움말 (`F1`)

우측 메뉴의 **[? 도움말]** 또는 `F1` 로 사용법 가이드 팝업을 연다. 보고 있던 탭의 설명으로 바로 이동하며, 모든 단축키 표가 들어 있다.
도구·단축키 표는 `src/model/ui.ts` 의 정의(메뉴와 키 처리가 쓰는 것과 같은 데이터)에서 만들어지고, 사용법 설명은 `src/help/guide.ts` 에 있다.
**기능을 추가·변경하면 같은 변경 안에서 도움말도 고친다**(CLAUDE.md). `src/help/guide.test.ts` 가 실제 키 처리와 도움말을 대조해 누락을 잡는다.

### 단축키

| 분류 | 키 |
|---|---|
| 파일 | `Ctrl+O` 열기 · `Ctrl+S` 저장 · `Ctrl+P` 인쇄 · `F1` 도움말 |
| 이동·보기 | `←/→` `PgUp/PgDn` 이전/다음 쪽 · `Home/End` 첫/마지막 쪽 · `Ctrl+휠` 배율 · 쪽의 맨 위·아래에서 휠을 더 굴리면 이전·다음 쪽 |
| 편집 | `V` `T` `P` 도구 · `Ctrl+Z` 실행 취소 · `Ctrl+Y`/`Ctrl+Shift+Z` 다시 실행 · `Esc` 선택 도구·입력 확정 · `Delete`/`Backspace` 선택 항목 삭제 |
| 분할 | (분할 탭) `Enter` 그룹 종료 → (파일명 입력란) `Enter` 이름 확정 후 다음 묶음의 첫 쪽으로 |
| 캡처 | `C` 영역 캡처 도구 · (이름 입력란) `Enter` 확정 |
| 마우스 | 썸네일 클릭/`Ctrl`·`Shift`+클릭/끌기 · 썸네일 사이 ✂ · 분할선 끌기/더블클릭 · 파일 끌어다 놓기(`Shift` = 병합) |

입력란에 글자를 치는 동안에는 한 글자 단축키와 이동 키가 동작하지 않는다.

## 파일 크기 정책

- **기본 저장은 항상 무손실**: 이미지·폰트 스트림은 재압축 없이 바이트 그대로 복사하고 구조(object stream)만 압축한다.
  `e2e/lossless.e2e.ts` 가 분할 저장·편집 저장에서 이미지·폰트 스트림의 해시가 원본과 같은지 검증한다.
- **용량 최적화 저장(선택, 파일 탭)**: 기준 해상도(기본 300dpi)를 *넘는* 8비트 회색조·컬러 이미지만 기준 해상도까지 줄인다.
  쪽의 XObject 뿐 아니라 폼 XObject 가 (몇 겹이든) 품고 있는 이미지도 살핀다.
  기준 이하 이미지, 1비트 흑백 스캔(CCITT/JBIG2), 마스크·투명도·CMYK·JPX 이미지는 건드리지 않는다.
  다시 인코딩한 결과가 10% 이상 작지 않으면 원본을 유지한다. 원본 파일은 바뀌지 않는다(다른 이름으로 저장).
  해상도는 "이미지가 쪽을 가득 채워 그려졌다"고 가정한 하한값으로 판단하므로, 결과의 유효 해상도는 기준 이상이다.

## 구조

```

  model/      순수 로직: 좌표 변환(geometry), 분할 그룹(groups), 캡처 목록(captures), 텍스트 배치(textLayout),
              저장 계획(plan), 삽입 항목 기록 형식(editsCodec),
              메뉴·도구·단축키 정의(ui — 도움말과 공유하는 단일 출처)
  help/       도움말 본문(guide)과 실제 기능 대조 테스트
  pdf/        PDF.js 로딩·문서 정보 확인(loader)·렌더·캐시·목차·본문 텍스트
  engine/     저장 엔진(Web Worker, pdf-lib): 원본 1회 파싱 → copyPages → 저장, 선택적 이미지 최적화(optimize),
              재편집 기록과 복원(pieceInfo)
  actions/    파일 열기/저장/분할 저장/인쇄(io), 현재 쪽에서 그룹 종료(split), 캡처 렌더·일괄 저장(capture)
  components/ PageView · TextLayerView · Overlay · TextBoxView · Thumbnails · SidePanel · CaptureTab · EditTab · HelpDialog
  store.ts    상태(zustand). 편집은 비파괴 목록 + 실행 취소 기록
  devTune.ts  개발·자동화 전용 조정값(빌드본에서는 항상 비어 있다)
  sw.template.js  서비스 워커 원본(빌드 때 사전 캐시 목록이 채워져 dist/sw.js 가 된다)
e2e/          Playwright 테스트(*.e2e.ts = 개발 서버, *.pwa.ts = 빌드본·오프라인)
bench/        샘플 생성·벤치마크·스크린샷 스크립트
docs/         배포 계획(DEPLOY.md), 인수인계·작업 기록(HANDOFF.md)
.github/      CI(타입 검사·단위·E2E)와 GitHub Pages 배포 워크플로
```

## 벤치마크·개발 스크립트

```bash
npm run bench:sample          # bench/samples/sample_500p.pdf 생성(196MB · 500쪽 스캔본 모사, 페이지 트리가 평평하다)
npm run bench:split           # Node 에서 분할 속도 측정(파싱 → 20개로 분할 → 저장)
npm run bench:open            # (개발 서버 필요) 브라우저에서 열기 → 첫 화면 시간. 통째 읽기 / 구간 읽기(청크 크기별) 비교
npm run bench:thumb           # (개발 서버 필요) 썸네일 렌더 방식 비교
node bench/make-test.mjs      # 좌표 검증용 12쪽 샘플(회전·CropBox 혼합). E2E 가 쓰며 global-setup 이 자동으로 만든다
node bench/font-test.mjs      # 한글 폰트 임베딩·서브셋 검증
node bench/shot.mjs <split|text|capture|pen|file|help>   # (개발 서버 필요) 화면 캡처 → bench/out/shot-*.png
```

속도에 영향을 줄 수 있는 변경은 이 스크립트로 전후를 재서 함께 제안한다(CLAUDE.md 규칙 3).

| 항목 | 샘플 | 결과 |
|---|---|---|
| 열기 → 첫 화면 (`bench:open`, 디스크 읽기 포함) | 196MB · 500쪽 | 0.70초 |
| 20개 파일로 분할 (읽기·파싱 포함) | 196MB · 500쪽 | 약 2.5초, 출력 합계 = 원본 크기 |
| 텍스트 4개 삽입 후 저장 | 12쪽 · 10KB | 약 0.09초 |

측정 조건: Edge · 개발 서버 · i5-9500 데스크탑. 첫 줄은 `bench:open`(파일을 OPFS 에서 읽으므로 디스크 읽기가 들어간다)의
3회 중앙값(2026-09-19)이고, 다른 기기에서는 같은 측정이 1.19초였다. 아래 두 줄은 앱 안에서 잰 값이라 파일이 이미 메모리에 있다 —
디스크 읽기가 빠져 있어 첫 줄과 같은 잣대가 아니다(2026-09-18). 절대값은 기기·부하에 따라 달라지므로 같은 환경에서 전후를 비교한다.

구간 읽기 청크 크기 비교(`bench:open`, 통째 읽기 대비): 8/32/64MB 가 0.62/0.61/0.62초(i5-9500), 1.25/1.35/1.27초(다른 기기).
청크 크기 사이에도, 통째 읽기와의 사이에도 기기 간 편차를 넘는 차이가 없다 — 페이지 트리가 평평한 PDF 는 구간 읽기로 열어도
결국 파일 전체를 훑기 때문이다. `RANGE_CHUNK`(8MB)는 그대로 둔다.

## 알려진 제한

- 1GB 초과 파일은 구간 읽기(Range)로 열며, 페이지 트리가 평평한 PDF 는 파일 전체를 훑느라 여는 데 시간이 걸릴 수 있다(위 측정 참고).
- 전자서명된 PDF 를 수정·저장하면 서명이 무효가 된다(저장 전에 확인을 받는다). 서명 여부는 AcroForm 의 SigFlags 로 판단한다.
- 삽입한 텍스트·펜 선의 재편집은 이 앱으로 저장한 파일을 이 앱에서 열 때만 된다. 다른 프로그램이 콘텐츠 스트림을 합치는 등
  구조를 바꿔 다시 저장한 파일에서는 본문에 고정된 채로 열린다.
- 본문 검색 기능은 없다(글자 선택·복사는 된다). 스캔 이미지로만 된 PDF 에는 선택할 글자가 없다.
- 캡처 한 장은 1억 2천만 픽셀까지다(A4 전체 600dpi ≈ 3,500만 픽셀은 가능).
